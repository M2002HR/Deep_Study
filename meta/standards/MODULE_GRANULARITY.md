# استاندارد ریزدانگی Study PDF

هدف این استاندارد این است که تمام‌کردن هر PDF **یک پیشرفت واقعی و قابل تعریف** باشد.

## اصل اصلی

اندازه سند را با تعداد صفحه تعیین نکن. اول یک جمله بنویس:

> «بعد از تمام‌کردن این سند، learner دقیقاً چه چیزی را می‌تواند بفهمد، توضیح دهد، اجرا کند یا debug کند که قبل از آن نمی‌توانست؟»

اگر جواب یکپارچه نیست، scope احتمالاً بیش از حد بزرگ است.

## اندازه پیش‌فرض

برای بیشتر Study PDFهای Core:

- حدود 3 تا 8 ساعت مطالعه فعال همراه با تمرین/Lab؛
- معمولاً 20 تا 60 صفحه با layout فعلی؛
- حدود 2 تا 7 outcome اصلی؛
- حداقل یک مشاهده/Lab واقعی اگر موضوع عملی است؛
- failure/misconception و assessment مستقل.

این اعداد **قانون سخت نیستند**. انسجام مفهومی از page count مهم‌تر است.

## چه زمانی split کن؟

اگر یکی از این‌ها درست است، تقسیم سند را جدی بررسی کن:

- بیش از یک owner concept مستقل دارد؛
- برای توضیح scope باید چند بار «و همچنین...» بگویی؛
- بیش از حدود 8 outcome مستقل دارد؛
- Labها به چند محیط یا skill کاملاً جدا نیاز دارند؛
- بخش‌های سند dependencyهای متفاوتی دارند؛
- سند به حدود 70+ صفحه رسیده چون چند موضوع مستقل کنار هم قرار گرفته‌اند؛
- learner بعد از اتمام نمی‌تواند در یک جمله بگوید چه milestoneی را رد کرده است.

## چه زمانی merge کن؟

اگر سند:

- کمتر از حدود 10 تا 12 صفحه است؛
- mastery gate مستقل ندارد؛
- فقط یک جزئیات کوچک از owner document دیگری است؛
- Lab/failure/assessment معنادار مستقل ندارد؛

احتمالاً بهتر است زیرماژول سند مالک باشد، مگر اینکه reference مستقل بودنش ارزش واقعی داشته باشد.

## ترتیب تصمیم

1. owner concept
2. mastery outcome
3. dependency boundary
4. lab/failure boundary
5. حجم مطالعه
6. page count

page count آخرین معیار است، نه اولین معیار.

## ریزدانگی DKR.01 به‌عنوان نمونه

`DKR.01` یک Study PDF مستقل است چون یک outcome روشن دارد: ساخت مدل ذهنی درست از container و مرز آن با process/VM/system container و ecosystem؛ جزئیات namespace/cgroup/runtime internals را فقط در حد model معرفی می‌کند و مالک جزئیات را به ماژول‌های بعدی می‌دهد.
