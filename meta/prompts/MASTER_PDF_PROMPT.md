# MASTER PDF PROMPT - Deep Study

**Status:** Canonical, project-wide  
**Applies to:** every Deep Study syllabus, study PDF, workbook, report-like artifact and future revision  
**Primary font override:** Vazirmatn  
**Core rule:** PDF is not complete until full visual QA of every rendered page passes.

## 0. Precedence and preservation

این prompt روی checklist اصلی کاربر بنا شده است و **هیچ‌یک از ۶۴ قاعده‌ی اصلی حذف نشده است**؛ متن اصلی به‌صورت کامل در Appendix A حفظ شده و نسخه‌ی بدون تغییر آن نیز در `meta/prompts/source/REPORT_GENERATION_PROMPT_ORIGINAL.md` نگهداری می‌شود.

در صورت تعارض، precedence این است:

1. explicit instruction همان task/document؛
2. Deep Study project overrides در این master prompt؛
3. checklist اصلی Appendix A.

### Deep Study overrideهای صریح

- هر مثال checklist درباره‌ی «بی‌نازنین» برای این repository با **Vazirmatn** جایگزین می‌شود. هدف بندهای اصلی - یکدستی و embedding واقعی فونت - بدون تغییر حفظ می‌شود.
- بخش‌های مخصوص «تکلیف دانشگاهی» در Deep Study به معنای document/report quality constraints اعمال می‌شوند؛ اگر metadata دانشجویی/نیم‌سال موضوع سند نیست، placeholder بی‌معنی ساخته نشود.
- PDF مطالعه محصول نهایی مصرفی است؛ Markdown/structured source منبع canonical قابل version-control است.

## 1. Mandatory pre-research gate

قبل از نوشتن:

1. `AGENTS.md`, `CONTENT_STANDARD.md`, `SOURCE_POLICY.md`, `RESEARCH_METHOD.md`, `MASTERY.md` را بخوان.
2. syllabus و Scope Contract همان Document ID را بخوان.
3. owner documentهای prerequisite و upstream/downstream را شناسایی کن.
4. source set canonical را تعیین کن.
5. تمام claimهای version-sensitive را **در زمان تولید** verify کن.
6. research cutoff و source baseline را ثبت کن.
7. gap یا disagreement حل‌نشده را پنهان نکن.

## 2. Cross-document synchronization gate

قبل از draft جدید:

- terminology registry را load کن؛
- تکرار مطلب را با owner documentها audit کن؛
- IDها و cross-referenceها را validate کن؛
- version/source baselineهای مشترک را compare کن؛
- اگر upstream تغییر کرده، impact روی downstream را فهرست کن؛
- style/metadata/box/table/citation conventions باید با آخرین canonical PDFهای پروژه سازگار بمانند.

## 3. Required Scope Contract

هر Study PDF باید قبل از متن آموزشی این قرارداد را داشته باشد:

- Document ID / Version / Status
- Research cutoff / Last reviewed
- In Scope
- Out of Scope
- Prerequisites
- Assumed knowledge
- Upstream dependencies
- Downstream dependencies
- Version-sensitive areas
- Source baseline
- Mastery evidence expected

هیچ سندی نباید ادعای «کامل بودن» خارج از scope خود داشته باشد.

## 4. Required mastery-content schema

در صورت relevance، سند باید این لایه‌ها را پوشش دهد:

`Why -> terminology/invariants -> mental model -> architecture/state -> mechanics -> operations -> internals -> interfaces/reference surface -> connections -> security -> performance -> production -> failure modes -> debugging -> labs/experiments -> source/spec reading -> misconceptions -> interview ladder -> teach-back -> mastery checklist -> references/changelog`

اگر بخشی relevant است و حذف می‌شود، دلیلش در Scope Contract ثبت شود.

## 5. Source and citation requirements

- memory-only generation ممنوع است.
- normative claims از spec؛ current behavior از official docs/release notes؛ implementation claims از source/tests.
- secondary source فقط مکمل است.
- claim مهم نزدیک evidence citation داشته باشد.
- implementation-specific reading بهتر است tag/commit/path داشته باشد.
- quote طولانی copyrighted نکن؛ synthesize/paraphrase کن.
- کتاب تجاری در repo قرار نده مگر license اجازه دهد.

## 6. Typography and layout - Deep Study canonical

- زبان اصلی PDFهای فارسی: RTL واقعی.
- فونت اصلی **Vazirmatn** برای body، heading، table، box، caption، footer و اعداد فارسی.
- استفاده‌ی واقعی/embedding فونت باید با ابزار preflight مانند `pdffonts` یا equivalent verify شود؛ صرفاً نام CSS کافی نیست.
- command/path/hash/version/API/DOI و متن فنی لازم LTR و Latin باقی می‌ماند؛ bidi باید visually verify شود.
- اعداد در prose فارسی فارسی باشند؛ version/hash/command/protocol values طبق شکل canonical خود Latin بمانند.
- A4 و حاشیه‌ی امن پیش‌فرض؛ page border ظریف؛ footer consistent؛ رنگ محدود و رسمی.
- heading orphan، table-header orphan، bad box split و clipping ممنوع.
- TOC فقط بعد از pagination نهایی معتبر است و باید true RTL باشد.

## 7. PDF generation workflow - non-negotiable

1. canonical source را نهایی کن.
2. PDF candidate بساز.
3. structural preflight اجرا کن: page count، metadata، font embedding، extractability، suspicious empty pages، file integrity.
4. PDF را با renderer معتبر در 180-220 DPI به image تبدیل کن.
5. **تمام صفحات، بدون استثنا، از نظر بصری بررسی شوند.**
6. بررسی ویژه: cover، TOC، page numbers، border، headings، code/English bidi، tables، boxes، references، long URLs، page breaks، blank pages، glyphs و font consistency.
7. defect list بساز.
8. source را اصلاح کن - نه فقط PDF binary را.
9. PDF را دوباره تولید کن.
10. دوباره همه صفحات را render و بررسی کن.
11. این loop تا صفر شدن defect واضح ادامه یابد.
12. تنها final PDF و canonical source versioned شوند؛ renderهای QA و font binaries deliver/commit نشوند.

**Visual QA یک توصیه نیست؛ shipping gate است.**

## 8. Regression rule

هر revision از آخرین نسخه‌ی صحیح ساخته می‌شود. اصلاح جدید نباید fixهای قبلی مثل font، RTL، TOC، numbers، margins، border، boxes یا pagination را برگرداند. بعد از هر تغییر layout-sensitive باید regression visual QA دوباره انجام شود.

## 9. Syllabus-specific requirements

Syllabus باید علاوه بر محتوای curriculum، این‌ها را داشته باشد:

- mission و mastery ladder؛
- phase/module taxonomy و stable IDs؛
- dependency chains/DAG؛
- source baseline + currentness policy؛
- module-level coverage، labs/failures/source/spec tasks؛
- gates و Definition of Done؛
- coverage matrix schema؛
- روش استخراج/به‌روزرسانی syllabus؛
- PDF/document production contract؛
- pair-study protocol؛
- contribution/interview/capstone milestones؛
- changelog/version policy.

## 10. Module-PDF coordination protocol

برای ساخت اولین و همه‌ی PDFهای بعدی:

- module source filename و PDF filename باید Document ID و version یکسان داشته باشند؛
- front matter باید cross-referenceهای syllabus را ثبت کند؛
- اگر concept متعلق به PDF دیگری است، summary حداقلی + reference بده؛ duplicate deep explanation نساز؛
- اصطلاح/diagram convention جدید در registry ثبت شود؛
- discovery جدیدی که syllabus gap است ابتدا در coverage/gap log ثبت و سپس syllabus update شود؛
- downstream invalidation پس از تغییر foundational doc ثبت شود.

## Appendix A - Original 64-rule checklist (preserved verbatim)

## چک‌لیست عمومی برای تولید PDF تکلیف و گزارش‌های دانشگاهی

۱. **ابتدا صورت تمرین را کامل بخوان.**
قبل از نوشتن پاسخ یا طراحی PDF، همه بندهای تمرین، نمره‌ها، بخش‌های اصلی، بخش‌های اختیاری، ضمائم لازم، نام‌گذاری فایل، محدودیت‌ها و نکات تکمیلی را استخراج کن.

۲. **دامنه کار را مشخص کن.**
اگر تمرین چند بخش دارد، دقیقاً مشخص کن کدام بخش باید انجام شود؛ مثلاً فقط «بخش انفرادی» یا فقط «بخش کارگاهی». از پاسخ دادن به بخش‌هایی که کاربر نخواسته، پرهیز کن.

۳. **پاسخ را بر اساس محتوای کلاس تولید کن.**
اگر کاربر متن کلاس، جزوه، ترنسکریپت یا فایل آموزشی داده است، چارچوب پاسخ باید با همان آموزش هماهنگ باشد؛ نه صرفاً یک پاسخ عمومی. اصطلاحات، مدل‌ها، ترتیب مفاهیم و معیارهای گفته‌شده در کلاس باید رعایت شوند.

۴. **از لحن طبیعی دانشجویی استفاده کن.**
متن نباید شبیه خروجی خام هوش مصنوعی باشد. از عبارت‌های کلیشه‌ای، توضیحات بی‌دلیل، مقدمه‌چینی مصنوعی و جمله‌های تبلیغاتی پرهیز کن.

۵. **پاسخ کامل باشد، اما اضافه‌گویی نداشته باشد.**
هر چیزی که تمرین خواسته باید انجام شود؛ اما توضیحاتی که ارتباطی با خواسته تمرین ندارد یا صرفاً برای پر کردن متن است حذف شود.

۶. **ساختار گزارش را از ابتدا مشخص کن.**
گزارش باید صفحه عنوان، فهرست مطالب، بخش‌های اصلی، زیربخش‌ها، جدول‌ها، پاسخ‌های تشریحی و در صورت نیاز فهرست منابع یا شناسه‌ها داشته باشد.

۷. **صفحه اول را مستقل و تمیز طراحی کن.**
در صفحه اول فقط اطلاعات اصلی بیاید؛ مثل عنوان گزارش، عنوان تمرین، نام درس، نیم‌سال، نام و نام خانوادگی، شماره دانشجویی و تاریخ. از شلوغ کردن صفحه اول با توضیحات اضافی پرهیز شود.

۸. **صفحه اول می‌تواند وسط‌چین باشد.**
برخلاف صفحات محتوایی، صفحه عنوان بهتر است مرکزچین و رسمی باشد؛ اما فقط برای همان صفحه. مرکزچین بودن نباید به صفحات بعدی منتقل شود.

۹. **اطلاعات هویتی را دقیق وارد کن.**
نام، شماره دانشجویی، تاریخ و نیم‌سال باید دقیقاً مطابق خواسته کاربر نوشته شوند. برای مثال، اگر نیم‌سال مربوط به سال تحصیلی ۱۴۰۴ و ۱۴۰۵ است، باید دقیقاً به شکل «نیم‌سال دوم سال تحصیلی ۱۴۰۴-۱۴۰۵» نوشته شود. بین ۱۴۰۴ و ۱۴۰۵ فقط خط تیره «-» قرار بگیرد؛ نه «تا»، نه «الی»، نه فاصله اضافی و نه علامت دیگر.

۱۰. **فونت اصلی را از ابتدا تعیین کن.**
برای متن فارسی از فونت خواسته‌شده کاربر استفاده کن؛ مثلاً «بی‌نازنین». همه متن‌های فارسی، تیترها، شماره صفحه‌ها و اعداد فارسی تا حد امکان باید با همان فونت نمایش داده شوند.

۱۱. **فونت اعداد را جداگانه و ناهماهنگ نکن.**
اعداد فارسی نباید با فونتی متفاوت، عجیب یا ناهماهنگ دیده شوند. اگر فونت جداگانه برای اعداد باعث ظاهر خراب می‌شود، اعداد را به‌صورت فارسی و با همان فونت اصلی متن وارد کن.

۱۲. **اعداد فارسی باشند.**
در متن فارسی از اعداد فارسی استفاده کن: ۱، ۲، ۳، ۴، ۵، ۶، ۷، ۸، ۹، ۱۰.
اعداد لاتین فقط در مواردی مثل DOI، عنوان انگلیسی مقاله، سال میلادی یا عبارت‌های انگلیسی لازم است.

۱۳. **جهت متن فارسی راست‌به‌چپ باشد.**
کل گزارش فارسی باید راست‌به‌چپ باشد. متن نباید در اثر ترکیب با انگلیسی به هم بریزد یا جهت نادرست پیدا کند.

۱۴. **بیشتر متن‌ها راست‌چین یا تراز از راست باشند.**
متن‌های توضیحی، پاراگراف‌ها، تیترها و بدنه اصلی باید راست‌چین باشند. از وسط‌چین کردن بی‌دلیل متن‌های اصلی پرهیز شود.

۱۵. **فقط موارد خاص وسط‌چین شوند.**
صفحه اول می‌تواند وسط‌چین باشد. جدول‌ها، بعضی سلول‌های جدول و عنوان‌های داخل جدول هم می‌توانند وسط‌چین باشند. اما متن‌های عادی، تیترهای محتوایی و توضیحات نباید وسط‌چین شوند.

۱۶. **تیترهای اصلی راست‌چین و بولد باشند.**
تیترهای اصلی باید واضح، پررنگ و در سمت راست صفحه قرار بگیرند. نباید بعضی تیترها به‌اشتباه به سمت چپ بروند.

۱۷. **تیترهای فرعی هم راست‌چین باشند.**
زیربخش‌ها باید از نظر رنگ، اندازه و وزن فونت از متن عادی متمایز باشند، اما همچنان راست‌چین و هماهنگ با ساختار فارسی گزارش بمانند.

۱۸. **از شماره‌گذاری فارسی برای تیترها استفاده کن.**
شماره بخش‌ها و زیربخش‌ها بهتر است فارسی باشد؛ مثل ۱، ۲، ۳ یا ۱.۵، ۲.۵. این شماره‌ها نیز باید از نظر فونت با متن هماهنگ باشند.

۱۹. **برای کل صفحات کادر بگذار.**
هر صفحه بهتر است یک کادر ساده، نازک و منظم داشته باشد. کادر نباید خیلی ضخیم، تیره یا نزدیک به متن باشد.

۲۰. **شماره صفحه درج کن.**
شماره صفحه باید در همه صفحات دیده شود، ترجیحاً پایین صفحه و وسط. متن شماره صفحه می‌تواند به شکل «صفحه ۳» باشد و عدد آن فارسی باشد.

۲۱. **حاشیه‌ها را استاندارد و امن تنظیم کن.**
متن نباید به کادر صفحه بچسبد. برای بالا، پایین، چپ و راست صفحه حاشیه کافی در نظر بگیر تا متن، جدول و شماره صفحه فشرده یا بریده نشوند.

۲۲. **فهرست مطالب را درست صفحه‌آرایی کن.**
در فهرست، عنوان هر بخش باید در منتهی‌الیه راست همان ردیف باشد و شماره صفحه در منتهی‌الیه چپ همان ردیف قرار بگیرد. فضای بین عنوان و شماره صفحه باید در تمام ردیف‌ها با نقطه‌چین یکنواخت پر شود. فهرست نباید وسط‌چین باشد و نباید عنوان‌ها در میانه صفحه رها شوند.

۲۳. **فهرست را بعد از صفحه‌بندی نهایی به‌روزرسانی کن.**
پس از اضافه کردن صفحه‌شکنی‌ها، جدول‌ها و اصلاحات ظاهری، شماره صفحات فهرست باید دوباره کنترل و اصلاح شود.

۲۴. **از فهرست خیلی شلوغ پرهیز کن.**
در فهرست فقط بخش‌ها و زیربخش‌های مهم آورده شوند. لازم نیست هر پاراگراف یا هر جدول کوچک وارد فهرست شود.

۲۵. **باکس‌های توضیحی یکدست باشند.**
اگر از کادرهای داخلی برای نکته، اصل، پرامپت، نتیجه یا توضیح استفاده می‌شود، رنگ، ضخامت خط، فاصله داخلی و فونت آن‌ها باید یکدست باشد.

۲۶. **متن داخل باکس‌ها باید تا عرض مناسب ادامه پیدا کند.**
متن داخل باکس نباید بی‌دلیل زود شکسته شود و وسط سطرهای کوتاه بماند. تنظیم عرض، چینش و تراز متن داخل کادر باید طوری باشد که خط‌ها طبیعی و کامل پر شوند.

۲۷. **عنوان داخل باکس‌ها راست‌چین باشد.**
اگر باکس عنوان دارد، عنوان آن باید سمت راست قرار بگیرد و با جهت فارسی هماهنگ باشد.

۲۸. **باکس‌ها نباید بدشکل بین صفحات بشکنند.**
اگر یک باکس طولانی است، یا باید کامل در یک صفحه جا بگیرد یا اگر مجبور به شکست است، شکست آن در محل مناسب انجام شود. بهتر است عنوان باکس در یک صفحه و محتوای اصلی آن در صفحه بعد نیفتد.

۲۹. **جدول‌ها ساده، خوانا و منظم باشند.**
جدول‌ها باید خطوط تمیز، فاصله کافی، ستون‌های متناسب و متن خوانا داشته باشند. سلول‌ها نباید بیش از حد فشرده باشند.

۳۰. **در جدول‌ها مرکزچین بودن مجاز است.**
برخلاف متن اصلی، در جدول‌ها باید محتوای سلول‌ها و عنوان ستون‌ها تا حد امکان وسط‌چین باشند، مگر اینکه کاربر صریحاً چینش دیگری بخواهد. متن داخل سلول‌ها باید هم از نظر افقی و هم از نظر عمودی خوانا و متوازن باشد.

۳۱. **عرض ستون‌های جدول را کنترل کن.**
اگر متن یک ستون طولانی است، عرض آن ستون را بیشتر بگیر. اگر ستون فقط شماره یا امتیاز دارد، عرض آن را کم‌تر بگیر.

۳۲. **عبارت‌های انگلیسی را کنترل کن.**
کلمات انگلیسی مثل DOI، Results، Conclusion، Rule-Set یا عنوان مقاله‌ها باید جهت درست داشته باشند و ترتیب متن فارسی را خراب نکنند.

۳۳. **DOI و شناسه‌ها را لاتین نگه دار.**
شناسه‌های DOI، عنوان‌های انگلیسی مقاله‌ها و نام نویسندگان خارجی بهتر است با حروف و اعداد لاتین نوشته شوند تا استاندارد بمانند.

۳۴. **در متن فارسی، ترکیب فارسی و انگلیسی را بازبینی کن.**
بعد از تولید PDF باید بررسی شود که عباراتی مثل «نتایج Results» یا «جمع بندی Conclusion» به هم نریخته باشند و نقطه، ویرگول و پرانتزها جای درست باشند.

۳۵. **از رنگ محدود و رسمی استفاده کن.**
برای تیترها می‌توان از یک رنگ رسمی مثل آبی تیره استفاده کرد. برای باکس‌ها هم رنگ‌های خیلی ملایم مناسب است. از رنگ‌های زیاد، تند یا نامتعارف پرهیز شود.

۳۶. **تیتر در انتهای صفحه تنها نماند.**
یکی از مهم‌ترین کنترل‌ها این است که تیتر یک بخش در پایین صفحه نیاید و محتوای آن به صفحه بعد منتقل نشود. اگر چنین شد، تیتر را همراه با محتوایش به صفحه بعد ببر.

۳۷. **صفحه‌شکنی‌ها را آگاهانه تنظیم کن.**
شکست صفحه باید از محل طبیعی انجام شود؛ مثلاً قبل از شروع بخش جدید، قبل از جدول بزرگ، یا قبل از باکس طولانی. شکست صفحه وسط یک واحد معنایی مهم، ظاهر گزارش را خراب می‌کند.

۳۸. **جدول با فقط عنوان ستون در انتهای صفحه شروع نشود.**
اگر جدول در پایین صفحه فقط با سرستون شروع می‌شود و ردیف‌هایش به صفحه بعد می‌روند، جدول را کامل به صفحه بعد منتقل کن.

۳۹. **باکس یا جدول نصفه در پایین صفحه رها نشود.**
اگر در پایین صفحه فقط ابتدای یک باکس یا چند خط کم از جدول می‌آید، بهتر است آن قسمت به صفحه بعد منتقل شود.

۴۰. **فضای خالی کنترل‌شده قابل قبول است.**
برای جلوگیری از تیترهای یتیم یا جدول‌های بدشکست، گاهی باقی ماندن کمی فضای خالی در پایین صفحه بهتر از شکست نامناسب است.

۴۱. **صفحه‌بندی نهایی را بعد از همه اصلاحات انجام بده.**
نباید قبل از نهایی شدن متن، شماره صفحات و فهرست را قطعی کرد. هر اصلاح در فونت، جدول یا صفحه‌شکنی می‌تواند تعداد صفحات را تغییر دهد.

۴۲. **PDF را حتماً به تصویر تبدیل و بررسی کن.**
بعد از تولید PDF، صفحات را به تصویر تبدیل کن و ظاهر واقعی آن‌ها را ببین. بررسی فقط از روی کد یا متن کافی نیست.

۴۳. **همه صفحات را از نظر ظاهری مرور کن.**
در بازبینی تصویری، فقط صفحه اول یا چند صفحه تصادفی را نگاه نکن. همه صفحات را از نظر کادر، شماره صفحه، تیترها، جدول‌ها، باکس‌ها، شکست صفحه و جهت متن بررسی کن.

۴۴. **صفحه اول را جداگانه کنترل کن.**
در صفحه اول باید اندازه فونت، فاصله‌ها، مرکزچین بودن، اطلاعات هویتی، تاریخ و نیم‌سال دقیق بررسی شود.

۴۵. **فهرست را جداگانه کنترل کن.**
در صفحه فهرست باید چیدمان عنوان‌ها و شماره صفحه‌ها جداگانه و با رندر تصویری بررسی شود: عنوان‌ها در منتهی‌الیه راست، شماره صفحه‌ها در منتهی‌الیه چپ، نقطه‌چین کامل و یکنواخت بین عنوان و شماره، شماره‌ها به‌روز و فارسی. اگر نقطه‌چین‌ها فقط در سمت چپ جمع شده‌اند یا عنوان‌ها وسط صفحه مانده‌اند، فهرست هنوز خراب است و نباید ارسال شود.

۴۶. **صفحات دارای جدول را جداگانه کنترل کن.**
در صفحه‌هایی که جدول دارند، بررسی کن که جدول از کادر بیرون نزده، متن‌ها روی هم نیفتاده، ستون‌ها فشرده نیستند و جدول بدشکسته نشده است.

۴۷. **صفحات دارای باکس را جداگانه کنترل کن.**
در صفحه‌هایی که باکس دارند، بررسی کن که متن داخل باکس کامل، خوانا، راست‌به‌چپ و با عرض مناسب باشد.

۴۸. **فونت‌های PDF را بررسی کن.**
بعد از خروجی گرفتن، کنترل کن که فونت اصلی واقعاً در PDF استفاده و جاسازی شده باشد. اگر قرار است فونت «بی‌نازنین» باشد، نباید بخش‌های فارسی با فونت دیگری بیفتند.

۴۹. **اعداد را بعد از رندر تصویری بررسی کن.**
حتی اگر در متن اعداد فارسی وارد شده باشند، باید در خروجی تصویری نگاه کنی که ظاهرشان عجیب، ناهماهنگ یا شبیه فونت دیگری نشده باشد.

۵۰. **از ارسال نسخه‌ای که هنوز مشکل واضح دارد خودداری کن.**
اگر در بازبینی تصویری تیتر جابه‌جا، عدد خراب، باکس بدشکسته، متن وسط‌چین اشتباه یا فهرست نامرتب دیده شد، باید قبل از ارسال اصلاح شود.

۵۱. **نام فایل خروجی روشن و قابل تشخیص باشد.**
نام فایل باید فارسی یا مطابق خواسته تمرین باشد و نشان دهد نسخه نهایی است؛ مثلاً شامل عبارتی مثل «نسخه نهایی» یا «صفحه‌بندی نهایی» باشد.

۵۲. **فقط فایل نهایی را برای کاربر لینک کن.**
در پاسخ نهایی، فایل‌های آزمایشی، تصویرهای رندر، فونت‌ها یا فایل‌های واسط را ارسال نکن. فقط PDF نهایی را لینک کن.

۵۳. **فونت آپلودشده را منتشر نکن.**
اگر کاربر فونت را برای ساخت PDF داده است، فقط از آن در تولید فایل استفاده کن و خود فایل فونت را در خروجی یا لینک نهایی قرار نده.

۵۴. **پس از هر بازخورد، اصلاحات قبلی را حفظ کن.**
اگر کاربر بعداً فقط درباره فهرست یا صفحه‌شکنی ایراد گرفت، اصلاحات قبلی مثل فونت بی‌نازنین، اعداد فارسی، کادر، شماره صفحه، راست‌چین بودن و صفحه اول نباید از بین بروند.

۵۵. **در اصلاحات رفت‌وبرگشتی به نسخه خراب قبلی برنگرد.**
هر نسخه جدید باید بر اساس آخرین نسخه صحیح ساخته شود، نه بر اساس نسخه قدیمی‌تر که قبلاً ایراد داشته است.

۵۶. **قبل از ارسال نسخه اصلاح‌شده، موارد قبلی و جدید را هم‌زمان چک کن.**
اگر کاربر گفت «فقط این مورد را درست کن»، باز هم باید مطمئن شوی اصلاح جدید باعث خراب شدن فونت، اعداد، راست‌چین بودن، فهرست یا صفحه‌بندی نشده است.

۵۷. **برای تکلیف‌های دانشگاهی، متن را رسمی اما ساده نگه دار.**
زبان گزارش باید دانشگاهی، دقیق و قابل ارائه باشد، اما نباید بیش از حد سنگین، مصنوعی یا غیرطبیعی شود.

۵۸. **اگر تمرین منبع یا DOI می‌خواهد، آن را کامل بیاور.**
برای مقاله‌ها، DOI، عنوان، نویسندگان، سال و محل انتشار را تا حد نیاز درج کن. DOI باید دقیق و خوانا باشد.

۵۹. **اگر تمرین جدول یا پیوست خواسته، حذفش نکن.**
بخش‌هایی مثل جدول فلشرها، جدول Rule-Set، فهرست DOIها یا نمونه پرامپت‌ها باید در گزارش بیاید، مگر اینکه کاربر صریحاً حذفشان را بخواهد.

۶۰. **نسخه نهایی باید از نظر بصری قابل تحویل باشد.**
در پایان، PDF باید طوری باشد که بدون توضیح اضافه بتوان آن را به‌عنوان گزارش دانشگاهی ارسال کرد: مرتب، خوانا، راست‌به‌چپ، دارای کادر، شماره صفحه، فهرست به‌روز، فونت یکدست، اعداد فارسی و صفحه‌بندی کنترل‌شده.

## نکات تکمیلی اضافه‌شده بر اساس بازخوردهای اصلاحی

۶۱. **فرمت نیم‌سال را دقیق و ثابت بنویس.**
برای گزارش‌های مربوط به نیم‌سال دوم سال تحصیلی ۱۴۰۴ و ۱۴۰۵، عبارت باید دقیقاً «نیم‌سال دوم سال تحصیلی ۱۴۰۴-۱۴۰۵» باشد. بین دو سال فقط خط تیره انگلیسی ساده قرار بگیرد و از «تا»، «الی»، خط تیره بلند، فاصله اضافه یا عبارت‌های جایگزین استفاده نشود.

۶۲. **فهرست مطالب باید راست‌به‌چپ واقعی باشد، نه ظاهراً مرتب.**
در فهرست، هر ردیف باید از سمت راست با عنوان شروع شود، تا سمت چپ با نقطه‌چین ادامه پیدا کند و در انتهای چپ همان ردیف، شماره صفحه قرار بگیرد. اگر شماره صفحه‌ها سمت چپ هستند اما عنوان‌ها وسط صفحه مانده‌اند، یا نقطه‌چین‌ها فقط در یک بخش کوتاه افتاده‌اند، خروجی قابل قبول نیست.

۶۳. **فهرست را حتماً بعد از رندر تصویری کنترل کن.**
برای فهرست فقط به کد یا خروجی متنی اعتماد نکن. صفحه فهرست را به تصویر تبدیل کن و مطمئن شو همه ردیف‌ها یک الگوی واحد دارند: عنوان در راست‌ترین نقطه، شماره صفحه در چپ‌ترین نقطه و نقطه‌چین کامل بین آن‌ها.

۶۴. **جدول‌ها باید از داخل هم مرتب باشند.**
در تمام جدول‌ها، عنوان ستون‌ها و متن سلول‌ها باید وسط‌چین و خوانا باشند. اگر یک ستون متن بلند دارد، عرض ستون را بیشتر کن تا وسط‌چین بودن باعث شکست بد یا فشردگی نشود.
